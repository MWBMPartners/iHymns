## BUG 1 — Musician-profile migration fails (#1824)

**Root cause (confirmed):** #1741 P2 (`migrate-musicians-rename.php`) renamed the 7 `tblCreditPe*`/
`tblCreditPerson*` BASE TABLES → `tblMusician*` and created UPDATABLE **VIEWS** under every old name
(`schema.sql` ~L2864-2897; `tblCreditPersonMembers` is now a VIEW over `tblMusicianRelations`). The P1
migration `migrate-musician-profile.php` still does `ALTER TABLE tblCreditPersonMembers ADD UNIQUE KEY
uq_group_member_rel …` → **error 1347 "not BASE TABLE"** on any env where P2 has landed (now all of them,
incl. fresh installs from schema.sql). Column ADDs skip (colExists true via the view); the ADD UNIQUE KEY
throws.

**Second half:** the registry probe (`migration-registry.php` `'musician-profile'` ~L1979-1992) checks
`!_migProbe_indexExists(…, 'tblCreditPersonMembers', 'uq_group_member_rel')` — a VIEW has no index rows →
reads "missing" → card stuck **pending forever** → "Apply all pending" keeps retrying → errors every time.
`migrate-musicians-rename.php`'s own Step-0 doc-block anticipated this false-negative for ITS re-run gate
but never fixed P1. Only `musician-profile` among the 4 P1 cards is affected (the other three target
`tblWorks`/`tblTunes`/`tblSongs`, which P2 does NOT rename).

**Fix (planned):** (1) migration script short-circuits to clean success when `tblMusicians` base table
exists / target is a VIEW, before any ALTER (mirror P2 Step-0 idiom). (2) probe short-circuits to
"applied" (return false) when `tblMusicians` exists. `tblMusicians`-exists ⟹ P1 already applied on the
renamed base tables (P2's precondition gate guarantees it). No schema.sql change needed. Keeps
`test-migration-registry.php` green (not the `fn=>true` pattern).

## BUG 2 — Editor credit autosave duplicates musicians (#1843)

**Root cause (confirmed):** `credits-tab.js` (500 ms debounce) → `credit_upsert` (`api2.php` ~L2528) →
`musicianPromote` (`musician_helpers.php` ~L1531) → `registerMusicianByName` (~L1360, find-or-create by
exact `uk_Name`). Role tables store free-text `Name`, no FK. Every intermediate spelling mints a junk
registry row. Credit row itself is fine (adopts `credit.id`, UPDATEs in place).

**Fix (planned):** server-side orphan reconciliation in `credit_upsert` (owner's option b, generalised) —
shared helper in `musician_helpers.php`; rename the orphaned, untouched previous-name row forward instead
of creating a new one; delete-and-find-existing on `uk_Name` collision; existence-gated for un-migrated
installs. NOT the 20-30 s debounce (too long; still leaks). Debounce number TBD from Fable plan (lean
500→~1000 ms to cut churn, not for correctness).
