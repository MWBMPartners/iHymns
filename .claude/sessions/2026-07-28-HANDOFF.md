### 🔒 OWNER-LOCKED: CCLI validity is FORMAT-ONLY. Do not "harden" it. (2026-07-30)

> "we cant verify ccli numbers - so we should be light (for now) on our ccli licence criteria. Ie we
> should allow ccli licenses must be all numbers, and of 'normal' length. we cant 100% verify them"

**There is no CCLI verification service we can call.** So a CCLI licence is valid when the number is
**well-formed**: all digits, 5–8 long, after stripping whitespace/`-`/`.`/`,` and a leading `#` or
`CCLI:` prefix. `includes/ccli_validator.php::validateCcliNumber()` **already implements exactly
this** — reuse it; never re-implement the rule (that fork is what #1668 exists to remove).

⚠️ **This overrode the remediation plan's §4.3 C1**, which had told Batch 2 to require
`tblUsers.CcliVerified = 1`. That would deny essentially everyone, because nothing can ever set the
flag truthfully at scale. **`CcliVerified` stays in the schema as an advisory curator trust signal —
it must NOT be a precondition of holding a licence.**

A future reader will be tempted to make this stricter. The reason not to is not laziness: the gate
is a **good-faith declaration check**, deliberately light, because the alternative is a control
nobody can satisfy. Revisit only if a real verification path appears.

### ✅ Batch 5 landed (`e644486b`) — setlists: no cap, tombstones, optional expiry
Protocol-2 detection = **presence of the `deleted` key** (even `[]`), not a version number. A
tombstoned id is **dead forever** — no timestamp comparison anywhere (`updatedAt` is a client clock).
Cap removal is a **413 rejection, never a truncation**. **Native apps unchanged** — they never send
`deleted`, so they keep today's #1649-guarded path byte-for-byte. Expiry converges on tombstones
(`Reason='expired'`) so expiry and deletion are ONE mechanism.
⚠️ **The migration must be RUN per env** via `/manage/setup-database` (web-run, never automatic).
Until then everything is existence-gated and behaves exactly as before.

### 🧭 THE METHOD LESSON OF THIS PROGRAMME — read this before writing another guard

Four consecutive rounds ended with a guard **green while the thing it guarded was broken**. The
root cause is now unmistakable and it is not carelessness:

> **Source inspection was used as the primary evidence for properties that have a runtime handle.**

Whether a predicate returns true for a *wrapped* 1213, whether a gate's polarity is right, whether a
probe is the strict one — those are **behaviours**. Pattern-matching source for them yields an
assertion about the file's *vocabulary*, and vocabulary survives any mutation that keeps the words.

The worked example is `songRelocateIsTransactionFatal()`. Guarded three ways:
1. **Inline per catch** → the rule held in one function while ELEVEN catch blocks between the
   relocate and `commit()` still swallowed. Reach was wrong.
2. **Extracted + source-inspected** (call sites mention the predicate; its body mentions `1213`,
   `1205`, `mysqli_sql_exception`) → a reviewer replaced the body with `return false;`, left the
   vocabulary in a dead `$fatalCodes` array, and the **whole suite stayed green** while every site
   resumed swallowing. Reach fixed; the reached thing unpinned.
3. **`tests/php/test-transaction-fatal.php`** — constructs exceptions, asserts the returned
   booleans, reads no source. A predicate cannot pass by CONTAINING the right words, only by
   ANSWERING correctly.

**Proof, run against the real tree:** with the body gutted,
`test-song-relocate-hardening.php` stays **GREEN** and `test-transaction-fatal.php` goes **RED**.

**The rule: when a property lives in a PURE function, test the function.** Reserve source inspection
for what has no runtime handle — "every call site does X", "no fragment carries an inline script",
"no page hardcodes a CDN version". That is what `test-song-relocate-funnels.php` and
`test-fragment-inline-scripts.php` do, and it is the right tool for that job.

⚠️ Also learned the hard way in 4c: **a remediation can introduce the bug it is removing.**
`songRedirectsTableReady($db, true)` (added by the same pass) wraps its cause in a plain
`RuntimeException`, and the predicate only type-checked the OUTERMOST exception — so a deadlock
inside that probe was swallowed again, through a brand-new code path added by its own fix. Six
guard holes remain, tracked on **#1691**; the code they guard is currently correct.

### 🗑️ #1692 — song deletion is PERMANENT. The three stages, and where each one lives

The finding: a delete is a hard `DELETE FROM tblSongs`. There is **no soft-delete column on that
table at all**, and **38 of the 41** FKs referencing `tblSongs(SongId)` cascade — including
`fk_Revisions_Song` (`schema.sql:1620`). So a delete destroys the song, its components, credits,
media links **and its entire revision history**. Only the URL survives, as a redirect row. Recovery
means restoring a database backup; there is no in-app undo and no revision left to roll back to.

| Stage | Issue | State |
|---|---|---|
| 1 — admin-only in the interim | **#1693** | ✅ `e3e7323b` |
| 2 — soft delete + admin-only purge | **#1694** | ⬜ the substantive work |
| 3 — curators soft-delete, admins review + notified | **#1695** | ⬜ blocked by #1694 |

⚠️ **The load-bearing design constraint for stage 2: RESTORE MUST BE PREVENTION, NOT REPAIR.**
Once the row is deleted the children are gone and nothing the app holds can rebuild them. `IsDeleted`
must KEEP the row and every read must filter it. Delete-and-reinsert cannot work; neither can
"snapshot before deleting", which would have to reproduce ~40 tables faithfully.

⚠️ **`delete_songs` is the ONE deliberate non-equivalence in the Batch 6 entitlement map.** Every
other key was aligned so the wired check answers exactly what the raw gate answered. This one was
narrowed on purpose. It is recorded in three places so a future reader does not "fix" it back as
drift: the `$e1Baseline` table in `test-entitlement-parity.php`, the map comment in

# 🔒 DURABLE CONSTRAINTS

- **Three docroots, ONE MySQL.** `dev` / `beta` / `www` share a single database. A dropped column
  vanishes for all three at once, and mysqli runs STRICT so an ungated read **throws** rather than
  degrading.
- **`alpha` and `beta`/`main` have UNRELATED histories** (#1600). No merge-base. The promotion needs
  a deliberate tree replacement, not a merge — PR #1580 was closed unmerged for this reason.
- **Migrations are web-run, never auto-applied.** "It's in `schema.sql`" ≠ "it exists on alpha".
- **In git ≠ on the docroot.** #1642: a migration script existed in the repo and not on dev, blocking
  the whole "Apply all" mechanism. `deploy.yml:214`'s change detection uses a fixed five-commit
  window; if a push's last five commits contain no deployable file, the entire deploy is skipped.
  `[deploy all]` in a commit message forces a full mirror.

# 🧠 LESSONS THAT COST SOMETHING

**The version bump is not cosmetic.** `version-bump.yml` fires on pushes to `beta` and `alpha`, but
a hand-merged batch can still land without one. `infoAppVer.php` drives the `?v=` cache-busters
**and** the service-worker cache version (#81) — so a client holding the old SW cache keeps serving
the pre-fix bundle. That is precisely the "looks alive, does nothing" failure of #1565. **Check the
version moved after any large alpha batch.**

**`git add <paths>` does NOT clear a pre-existing index.** Twice a commit swept in another agent's
work; the second time, 207,000 lines of `songs.json` deletion landed inside the join-codes commit.
**While agents are running: `git diff --cached --name-only` FIRST**, and `git restore --staged`
anything that isn't yours. Otherwise a revert of one change silently undoes an unrelated one.

**Verify an agent's finding before acting on it.** Several were subtly wrong in detail while right in
conclusion — a "hardcoded 5-tier list" that didn't exist, a "10 gates" count that was nine. The
conclusions held; the specifics didn't. Checking cost one grep each time.
