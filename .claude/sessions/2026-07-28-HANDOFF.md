### Part 1 — three quick-win fixes

**#1576 — Service Mode ad-hoc sessions were born already expired.**
`serviceMode_occurrenceEndUtc()` had a hard *ceiling* but no *floor*, and the no-schedule-selected
path in `service_session_start` invents a placeholder occurrence (10:00, 90 min). Start an ad-hoc
session at 18:00 and its end resolved to 11:30 **that morning** — expired at birth, every join
rejected with a generic wrong-code toast. Now an `$isAdHoc` flag floors the end at
`now + max(duration, 15 min)`, still capped by the existing ceiling.

The floor is scoped to the ad-hoc path **only**, deliberately: an explicitly-scheduled occurrence
that genuinely finished stays honestly reported as expired. Flooring that too would mask a real
problem. Also fixed `service-projection.php`'s date default — it used `toISOString()` (a UTC date),
wrong for any venue west of UTC in the evening; now `toLocaleDateString('en-CA')`.

New test `tests/php/test-service-mode-occurrence.php`, 79 assertions, **proven able to fail**: the
fix was stashed and the test re-run against pre-fix code — ad-hoc assertions failed with drifts up
to 82,800 s (23 h in the past). Restored, 79/79 pass. (Rule from MEMORY: a test that has never been
proven to fail is worthless.)

**`migrate-json.php` — a single GET could TRUNCATE the live corpus.**
It is a legacy pre-#1010 bootstrap that truncates and re-imports from `songs.json`. It is reachable
from `/manage/setup-database` and had no confirmation gate. Now `confirm=1` (web) / `--confirm`
(CLI), positioned exactly like `restore.php` and `drop-legacy-tables.php`. The informational
preamble still runs unconfirmed as a safe preview; only the destructive half is gated. The card on
`setup-database.php` gained a loud warning and the existing `data-type-to-confirm` speed-bump

**HA integrity audit — the monthly job had failed silently since July.** Three compounding bugs, not

## 🔴 CI FAILURE HANDLED — #1559 latest-wins race (fixed, `4734ced4`)

The Apple `build` job went red on `0ce0ffb3` — a commit that touched **only `.claude/` markdown**,
which is what made it immediately obvious this was a latent race and not a regression.

Job `90293634454`: 3 issues, all one test —
`ProjectionViewModelTests.latestWinsOnOverlappingSelectSong`. A and B had swapped roles
(`finalResultA` came back `.shown` where `.failed("superseded")` was expected, and vice versa;
`viewModel.song?.songId` was `MP-9001` not `MP-9002`).

**The production code was right; the test was underspecified.** `selectSong` bumps
`fetchGeneration` **synchronously on entry**, so *latest wins* means latest-BY-ENTRY. The test
started both calls with back-to-back `async let` and only *afterwards* awaited either one's arrival
at the gated fetcher — which constrains nothing. When the runtime resumed B's child task first, B
took generation 1 and A took generation 2, making A the legitimate winner.

Fix: await A's arrival at the fetcher **before** issuing B. `waitUntilArrived` returns only once
that id has reached `GatedFetcher.fetch`, past the generation bump and parked on a continuation.

This is exactly the follow-on #1558's workflow comment predicted ("needs a real fix in the test's own
ordering guard"), and it is why `--no-parallel` could not help — **the race is inside the test, not
between suites.** The `apple.yml` comment now records that it has been done.

⚠️ **No Swift toolchain here**, so the fix is verified by reasoning about the generation guard and
the fetcher barrier, not by a local run. **CI on the PR is its first execution — confirm before
treating #1559 as closed.**

Adjacent, filed not fixed: **#1591** — `HeadlessRelayDriverLoopbackTests.bufferedCommandsArriveInOrder`
has the same unordered `async let` shape, and its order assertions are tautological (each `#expect`
re-asserts the predicate that located the event), so it cannot fail on the property its name claims.
Green today; left alone deliberately.

## The version-bump trap — worth internalising

The batch merged to `alpha` **without a version bump**, and that is not a slip: `version-bump.yml`
triggers **only on a push to `beta`**. Since nearly all work targets `alpha`, the version sits
still for long stretches — 98 commits shipped under one string.

Bumped by hand in `bad5ca4f` to **`0.4001.0`**, deliberately following the workflow's own arithmetic
(`MINOR=$((MINOR + 1))`, `PATCH=0`) rather than a rounder-looking number, so this file and the
automation can't disagree about what a minor bump means.

**The bump is not cosmetic here.** `infoAppVer.php` drives the `?v=` cache-busters *and* the
service-worker cache version (#81). The export fix and Present mode ship as **new ES modules**, so a
client still holding the old SW cache would keep serving the pre-fix bundle — exactly the

### The theme: payload gating is not asset gating

`contentGatingApply()` carefully strips a copyrighted lyric body from `song_detail` — and then the

per-song gate its neighbours don't honour is not a gate.**

| `song-media.php` gains a **second** gate: the tier cap for the media kind, alongside the entity gate | `song-media.php` |

### The one new shared function

`song-media.php` needed the same kind→cap mapping `contentGatingApply()` already had. Rather than a
third copy, it was extracted as **`contentGatingMediaAllowed($kind, $userId, $presenceToken)`** in
`content_gating.php`. The two are deliberately kept in lockstep — **a cap that hides the button but
not the file, or the reverse, is worse than neither.** Caps resolve through the registry-backed
`checkTierAccess()`; no local matrix (rule #28B); fail-open (rule #28C).

### Judgement calls worth remembering

- **The `auth_register` "redundant" COUNT is not redundant.** It decides *registration mode*, runs
  before validation, and holds no lock. The genesis-role decision is a separate read under
  `FOR UPDATE` inside a transaction. Commented in place so nobody merges them.
- **The CSRF tightening LOGS its rejections** (method + URI). It touches the exact path #1590 built
  to stop the sporadic editor "CSRF error"; a silent regression there would be miserable to
  diagnose. Per the Fetch spec browsers send `Origin` on every non-GET, so absent-both genuinely
  means "not a browser POST".
- **Logout deliberately spares `MEDIA_CACHE` / `SAVED_CACHE`.** Those are deliberate user downloads;
  wiping them on sign-out destroys intent, and they are re-gated on next fetch anyway.
- **The cross-org join collision was NOT fixed here** — it is a UX decision (freshest-wins vs "that
  code expired"), and it should not ride in on a security commit. Split to **#1621**.

### 2. #1622 — script injection in `version-bump.yml` (NEW, found by the push above)

The #1611 push turned **Version Bump red on beta**, and the cause was not the change — it was the
commit message.

Beta/main's `version-bump.yml:94` did:

```yaml
run: |
  COMMIT_MSG="${{ github.event.head_commit.message }}"
```

`${{ }}` substitutes **textually before the shell parses anything**, so the commit message is script
source. The cherry-picked message quoted the phrase `"DRY RUN — nothing has been changed"`; the
embedded `"` closed the assignment and the shell took the next word as a command —
`RUN: command not found`, exit 127.

**Proven locally rather than assumed**, both halves:

- The quoted-phrase message reproduces the exact CI error — and leaves `COMMIT_MSG` **empty**, so
  bump-type detection would silently mis-classify even without the error.
- A message containing `$(echo INJECTED-CODE-RAN >&2)` **executes it**. Confirmed by running it, not
  inferred — "arbitrary code execution" is a claim worth being sure about. The job holds
  `contents: write`.

Fixed on both: **`1ca0ccbd`** (beta) / **`aa1e2c60`** (main) — the value now arrives as an `env:`
variable, which the process receives verbatim and the shell never re-parses. Alpha's lineage
**already had this fix**; it simply had no path across the unrelated histories.

⚠️ **No green Version Bump run yet, and that is expected**: the workflow's own `paths:` filter covers
`appWeb/**`, `appApple/**`, `appAndroid/**`, `tools/**`, `data/**` — **not** `.github/**`, so a
workflow-only commit correctly does not re-trigger it. The next content push to beta exercises it.
Do not read the absence of a run as the absence of a fix. The one red run in the history is
`cd678484` — the run that FOUND the bug; a GitHub re-run would use that commit's own (still buggy)
workflow file, so it cannot be made retroactively green.

**Lead worth following:** beta's `version-bump.yml` also failed at `f852baed` (2026-04-24), same
workflow, same job. If that is the same cause, this has been intermittently breaking the version
bump for three months — firing only on messages containing a quote or shell metacharacter, which is

helper; `test-event-names.js` immediately failed with `dispatchers=0 listeners=1`, because it
verifies a real dispatcher by matching `dispatchEvent(new CustomEvent(<CONST>` textually. The fix
was to inline the pattern, **not** to loosen the scanner — a guard satisfiable by indirection
verifies nothing, and this is the exact #1581 class. `safely(fn)` survives for the try/catch, with a
comment telling the next person not to tidy it back.

## 🎵 #1533 SETLIST PLAYBACK + #1623 REVISIONS AUDIT (LANDED, `6b7b2c03`) — wave 2 COMPLETE

### #1533 — the bug underneath the feature

The issue read as "add playback controls". The real defect was that
**`getNavigation()` looked the list up by id in `getAll()`** — and a **shared** setlist has no local
record, so `getById()` returned `null` and shared lists could not be navigated **at all**, however
you reached them. Replaced by a playlist **context** carrying its own song order, which serves a
shared and an own list identically. `activeSetListId` survives as the fallback because
`applyCustomArrangement()` reads it.

~40% already existed from #94 (prev/next, position, disabled ends) — this **extends** it. Do not
build a parallel nav component.

**Arming is now on TAP** from both the own-list detail and the shared-list view. The "Use" button was
the only entry point before and nobody pressed it.

**`sessionStorage`, deliberately not `localStorage`** — "I'm working through this list" belongs to
this tab's session. localStorage would resurrect last Sunday's service on the next song view and
leak the context between tabs.

### ⚠️ The trap that came with going fixed-position

The bar moved from an in-flow alert to `position: fixed` on `<body>` (the old one scrolled away
exactly when a musician mid-service needs Next). **A fixed element does NOT vanish when the SPA
swaps page content.** So:

- `renderSongNavigation()` tears down **before every early return**
- `router.js` calls it on **EVERY** navigation, not just song pages

Without both, the bar strands over the home screen. `tests/test-setlist-playback.js` pins the
ordering — it is exactly what a later "tidy the guard clauses to the top" would undo.

`body.has-playlist-bar` reserves matching padding so the bar cannot cover the final lyric line.

**Four files deliberately NOT migrated; three were not anticipated by the issue:**

observer through the thing that reacts to failure.
