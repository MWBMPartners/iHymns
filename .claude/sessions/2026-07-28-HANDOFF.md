### Part 1 — three quick-win fixes

**#1576 — Service Mode ad-hoc sessions were born already expired.**
`serviceMode_occurrenceEndUtc()` had a hard *ceiling* but no *floor*, and the no-schedule-selected
path in `service_session_start` invents a placeholder occurrence (10:00, 90 min). Start an ad-hoc
session at 18:00 and its end resolved to 11:30 **that morning** — expired at birth, every join
rejected with a generic wrong-code toast. Now an `$isAdHoc` flag floors the end at
`now + max(duration, 15 min)`, still capped by the existing ceiling.

The floor is scoped to the ad-hoc path **only**, deliberately: an explicitly-scheduled occurrence
that genuinely finished stays honestly reported as expired. Flooring that too would mask a real
problem. Also fixed `service-projection.php`'s date default — it used `toISOString()` (a UTC date),
wrong for any venue west of UTC in the evening; now `toLocaleDateString('en-CA')`.

New test `tests/php/test-service-mode-occurrence.php`, 79 assertions, **proven able to fail**: the
fix was stashed and the test re-run against pre-fix code — ad-hoc assertions failed with drifts up
to 82,800 s (23 h in the past). Restored, 79/79 pass. (Rule from MEMORY: a test that has never been
proven to fail is worthless.)

**`migrate-json.php` — a single GET could TRUNCATE the live corpus.**
It is a legacy pre-#1010 bootstrap that truncates and re-imports from `songs.json`. It is reachable
from `/manage/setup-database` and had no confirmation gate. Now `confirm=1` (web) / `--confirm`
(CLI), positioned exactly like `restore.php` and `drop-legacy-tables.php`. The informational
preamble still runs unconfirmed as a safe preview; only the destructive half is gated. The card on
`setup-database.php` gained a loud warning and the existing `data-type-to-confirm` speed-bump
(#1298).

**HA integrity audit — the monthly job had failed silently since July.** Three compounding bugs, not

land where the other looks; (3) the aggregator hardcoded a third, also-wrong guess. Fixed by
extracting `book_dir_for_site()` and adding `ha_audit_paths.py`, which derives both real paths by

## 🔴 CI FAILURE HANDLED — #1559 latest-wins race (fixed, `4734ced4`)

The Apple `build` job went red on `0ce0ffb3` — a commit that touched **only `.claude/` markdown**,
which is what made it immediately obvious this was a latent race and not a regression.

Job `90293634454`: 3 issues, all one test —
`ProjectionViewModelTests.latestWinsOnOverlappingSelectSong`. A and B had swapped roles
(`finalResultA` came back `.shown` where `.failed("superseded")` was expected, and vice versa;
`viewModel.song?.songId` was `MP-9001` not `MP-9002`).

**The production code was right; the test was underspecified.** `selectSong` bumps
`fetchGeneration` **synchronously on entry**, so *latest wins* means latest-BY-ENTRY. The test
started both calls with back-to-back `async let` and only *afterwards* awaited either one's arrival
at the gated fetcher — which constrains nothing. When the runtime resumed B's child task first, B
took generation 1 and A took generation 2, making A the legitimate winner.

Fix: await A's arrival at the fetcher **before** issuing B. `waitUntilArrived` returns only once
that id has reached `GatedFetcher.fetch`, past the generation bump and parked on a continuation.

This is exactly the follow-on #1558's workflow comment predicted ("needs a real fix in the test's own
ordering guard"), and it is why `--no-parallel` could not help — **the race is inside the test, not
between suites.** The `apple.yml` comment now records that it has been done.

⚠️ **No Swift toolchain here**, so the fix is verified by reasoning about the generation guard and
the fetcher barrier, not by a local run. **CI on the PR is its first execution — confirm before
treating #1559 as closed.**

Adjacent, filed not fixed: **#1591** — `HeadlessRelayDriverLoopbackTests.bufferedCommandsArriveInOrder`
has the same unordered `async let` shape, and its order assertions are tautological (each `#expect`
re-asserts the predicate that located the event), so it cannot fail on the property its name claims.
Green today; left alone deliberately.

## The version-bump trap — worth internalising

The batch merged to `alpha` **without a version bump**, and that is not a slip: `version-bump.yml`
triggers **only on a push to `beta`**. Since nearly all work targets `alpha`, the version sits
still for long stretches — 98 commits shipped under one string.

Bumped by hand in `bad5ca4f` to **`0.4001.0`**, deliberately following the workflow's own arithmetic
(`MINOR=$((MINOR + 1))`, `PATCH=0`) rather than a rounder-looking number, so this file and the
automation can't disagree about what a minor bump means.

**The bump is not cosmetic here.** `infoAppVer.php` drives the `?v=` cache-busters *and* the
service-worker cache version (#81). The export fix and Present mode ship as **new ES modules**, so a
client still holding the old SW cache would keep serving the pre-fix bundle — exactly the
