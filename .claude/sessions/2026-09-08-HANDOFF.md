## The find of the day: a rule that would have made things less safe

`CLAUDE.md` rule #49 says every outbound connection must use the one shared check for "is this
address somewhere we must refuse to connect to?", and never keep its own copy. `includes/webhooks.php`
keeps its own copy, so the obvious move is to delete it and use the shared one.

The issue said to compare them first. Running both against the same twenty addresses, **the shared
guard — the one the rule calls authoritative — was the weaker of the two**:

```
address            shared guard    webhook copy
100.64.0.1         public   <--    private
224.0.0.1          public   <--    private
```

Following the rule literally would have quietly reduced the app's protection while looking like
tidying up.

**Why the shared one was wrong.** It leaned entirely on PHP's built-in "is this private or reserved?"
question. That built-in is good but predates two things now being reserved:

- **100.64.0.0/10** — carrier-grade NAT. Internet providers and several hosting companies use these
  for their own internal plumbing. To PHP's filter they look like ordinary public addresses. Reaching
  one is the same class of mistake as reaching a cloud provider's credential service.
- **224.0.0.0/4** — multicast.

**Fixed in `42c6bf94`**: a small helper covering exactly those two, called alongside the built-in
check. The two now agree on all twenty addresses including the boundaries either side of the range.
SSRF guard 65/65, full suite 279/279.

**Why nobody spotted it:** the guard's own test was built from a list of outbound clients that did
not include webhooks. A rule #34 problem inside the guard meant to enforce rule #49.

**The general lesson, now in the code:** an instruction to consolidate onto a shared component is only
safe once you have checked the shared component is actually the better one.

Still to do on #2111: point `webhooks.php` at the shared guard, and add webhooks to the guard's test.

## #2112 QR — the owner was right, and it is worse than first reported

I originally said the extensionless address works on production because it returns HTTP 200. **Wrong**,
and it is the trap this repository already documents (#1566): the server answers *any* unrecognised
address with 200 and the whole web page.

```
https://ihymns.app/qr?data=hello       HTTP 200   96,336 bytes  text/html  <- the entire website
https://dev.ihymns.app/qr?data=hello   HTTP 503        0 bytes             <- "not configured"
```

Two separate faults:

1. **The QR service has no key.** Alpha, where the address IS mapped, correctly answers 503. So no QR
   can be produced anywhere today. The owner's instinct was right; this is a deployment step.
2. **On production the address is not mapped at all.** `main`'s `.htaccess` has no rule for it, so the
   browser is handed the whole 96 KB page where a small image should be — on every printed page with
   the QR block on.

Both already fixed on alpha. No code needed: the promotion, then a key when CueRCode is ready.

## Costs, measured

**Making the repository private: about $128/year**, from 1,072 runs and 1,726 jobs.

- Secret scanning and push protection: **$0 extra**. Billed per unique committer across the whole
  organisation; the owner is already a licensed committer via `dev-team-plugin`. Verified against the
  live billing API.
- ⚠️ **CodeQL: $360/year** — nearly three times the Actions cost, and free only while public. Turning
  it off costs nothing.
- ~$1/month is `auto-merge-alpha.yml` polling for up to 60 minutes with no timeout. Free while
  public, billed while private. Worth fixing either way.

**Apple builds are the growth area.** Apple CI runs on macOS at ten times the Linux rate, 9–11 minutes
a run — about $2/month today. Switching TestFlight on means every qualifying push builds, signs and
uploads; at roughly 20 minutes and 20 builds a month that is **~$25/month (~$300/year)**, which would
make Apple the largest single line. Android is on Linux and cheap.
