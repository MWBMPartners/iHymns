## 1. Offline version-proofing (#1962)

The deep audit (Fable) found the requirement was **not** already satisfied: the newer
`tblSongMedia` → `/song-media/<id>` family (#853) — which carries **all MusicXML** plus
curator-uploaded audio/PDF/MIDI — was cached in the **version-keyed `CACHE_VERSION` bucket
(wiped every deploy)** or not at all (Range→206 → `cache.put` rejected). A direct
invariant-(A) violation the earlier #1597 offline work never covered.

Fix (cheap, because `song-media.php` already emits a `Sha256` content-hash ETag):
- SW now recognises `/song-media/` as media (matched **ahead of** the navigation branch);
- `SongData::_songMediaMap()` content-stamps the stream URL `?song=<SongId>&v=<sha256:12>` — a
  changed file = a new key fetched once, unchanged = zero bytes; the change signal rides the
  existing #131 byte-compare (inherits `autoUpdateOfflineSongs`);
- media handler gained stale-while-revalidate (conditional `If-None-Match`), `bulk_audio` a
  conditional sync + the tblSongMedia audio rows, `audio-media.php` #1452-style validators;
- `songs_index` moved to a version-independent bucket; downloaded-songbook fragment warm-up;
- two pre-existing bugs fixed (206 `cache.put`; `bulk_audio` union 404s).
- Guards: extended `test-offline-cache-policy.js` + new tree-derived `test-offline-media-coverage.js`.

## 2. Versioning — the arc that mattered

**Started tag-based (#1963):** conventional-commit classifier (`classify-bump.sh`,
`feat`→minor / `!`/`BREAKING`→major / else→build-only) driving `v*` tag minting inside
`deploy.yml` (the one context that runs once per alpha landing — a standalone `on: push`
workflow is dead-on-arrival because `GITHUB_TOKEN` auto-merge pushes don't re-trigger `on: push`).
Merged in #1964.

**Then the owner flagged the real model:** *direct SFTP, no GitHub Releases* — and creating the
bootstrap `v1.1.0` tag from automation **403'd** (tag creation is restricted; branch pushes work).

**Pivoted to tag-free (#1965, PR #1966):** the anchor is now the **committed `Version.Number` in
`infoAppVer.php`** — `MAJOR.MINOR` authoritative, patch a placeholder. `deploy.yml`:
- resolves committed `MAJOR.MINOR` (all branches);
- on alpha, classifies commits since the last change to that line (a `git log -G` **pickaxe**
  anchor — idempotent, since the bump commit itself becomes the new anchor) and, on a
  feat/breaking, edits the committed value + `api-docs.yaml` + `manifest.json` and commits it
  back `[skip ci]` (a **branch push — never a tag**), worktree-isolated so the build-count
  arithmetic stays intact;
- injects `MAJOR.MINOR.<git rev-list --count HEAD>` for display **every** deploy (no gate).
- `release.yml` dormant (manual-tag-only); promotion bridge mints nothing.
- Guard: `test-versioning-pipeline.js` rewritten tag-free, mutation-proven (no `git tag`/
  `refs/tags`/release dispatch; committed anchor; classifier format-string lockstep).

**The 403 blocker is fully dissolved** — no tag is ever created, so nothing needs owner action.

**Mint on clear signals only:** the classifier's SAFE DEFAULT is build-only, so a mislabeled/bare
squash subject under-bumps (safe) rather than over-bumping. **The load-bearing convention now in
`CLAUDE.md` rule #46 + `MEMORY.md`:** title every PR/squash with a conventional-commit prefix, or
the minor silently won't move. This session's own conversion PR was deliberately titled
`refactor(ci):` so it self-classified build-only (a `feat:` title would have bumped it to 1.2).

## The build-number gotcha (record this)

`git rev-list --count HEAD` in **this remote container is a SHALLOW clone** (~59 commits deep), but
CI checks out `fetch-depth: 0` (full history) → the true count is **1009**. So a version predicted
from the local count is WRONG. I stated `1.1.59` several times; the real deployed value is
**`1.1.1009`** (confirmed in the deploy log: *"Injected version 1.1.1009 (committed anchor 1.1,
build 1009)"*). Verify build numbers from the CI deploy log, never the container's `rev-list`.
