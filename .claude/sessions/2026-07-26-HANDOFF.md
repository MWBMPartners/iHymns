## ✅ PART 2 — Public export was broken and always had been — FIXED, pushed

**User report:** Export ▾ → ProPresenter 7+ did nothing, on both a single song and a whole songbook.

**What it actually was:** **no export format had EVER worked on any public page.** The only code
binding those menu items was a nonce-less inline `<script>` inside the song/songbook fragment, and
the document sends an **enforcing nonce CSP** (#117) that refuses it. Bootstrap still opened the
dropdown, so the menu *looked* alive while nothing was bound — hence total silence, not even an error
toast (the "Preparing export…" toast is the first statement *inside* the never-attached listener).

Born broken: CSP shipped 2026-04-06 (`a21ea99f`), export UI shipped 2026-06-07 (`5dedf5d4`). Nothing
regressed — the two simply never met. **The lesson was already in the repo**: `home.php:379-387`
documents it verbatim, and `home-page.js` exists because of it. It just was never generalised.

| Commit | Fix |
|---|---|
| `7da63424` | **#1565** — wiring moved into `router.js afterPageLoad()`; IDs DOM-first from `.page-song[data-song-id]` / new `.page-songbook[data-songbook-abbr]`, route param as fallback; inline scripts deleted; dead `window.iHymnsExportUi` removed |
| `4abfc366` | **#1566** — `DEFAULT_BUNDLE_URL` → root-absolute `/manage/editor/protos/proto-bundle.json`; + the missing `await` on the single-song PP7 export |
| `f543c6fd` | **#1567** — editor v2 now loads `vendor/protobuf.min.js` before the exporter (PP7 had always failed there) |
| `f03a3e4b` | **#1568** — Present mode → `js/modules/present-mode.js`; fixes a leaked document `keydown` handler (old code listened for `'remove'`, not a DOM event) |
| `eeff40e0` | **#1570** — one shared `includes/partials/export-menu.php`; **ChordPro added to songbooks**; dead `FORMATS` deleted |
| `89cc2398` | **#1569** — CI guard + regression tests + node tests wired into CI |

**The second, masked bug (#1566)** would have bitten the moment #1565 was fixed: the proto-bundle URL
was document-relative, so from `/song/MP-1008` it fetched `/song/protos/proto-bundle.json` — which
the SPA catch-all answers **HTTP 200 with HTML**, so `response.ok` passed and `.json()` threw.

**Why nobody caught it:** the ProPresenter suite passed 54/54 while injecting the bundle straight
into `init()` — the runtime fetch path had **never once executed**. `export-ui.js` had zero coverage.
CI ran no node tests at all.

**Tests (#1569) — every one proven able to fail:**
- Reverting the bundle URL → `56 passed, 2 failed` (independently reproduced twice). Restored → 58/58.
- The new PHP guard, run in a detached worktree at `912dfe47`, flagged exactly `song.php` ×2 +
  `songbook.php` ×1 and correctly did **not** trip on the `<script>` mentions inside comments in
  `home.php` / `person.php` (that is what the comment-stripping step is for).
- Current: `test-propresenter-export.js` 58/58 · `test-export-ui.js` 7/7 ·
  `test-fragment-inline-scripts.php` PASS (23 files).

**Two judgment calls made rather than blocking** (flag if you disagree):
1. **ChordPro added to the songbook menu** — the exporter exists and is registered, and the song menu
   already offered it, so the omission was clearly accidental. Small user-visible behaviour change.
2. **`request-a-song.php` allowlisted** in the new CI guard rather than fixed now (#1572) — that page
   degrades safely to a full-page POST today, and its inline module embeds a PHP `filemtime`
