Each atomic, guarded (CSRF / role / `bind_param`), writing a coalesced `tblSongRevisions` (#400) + `logActivity` row, returning the true `{ok, affected_rows}`.
- **`delete_song` design note:** 40 FKs reference `tblSongs(SongId)`, only **16 CASCADE**. A complete delete must remove the whole subtree (incl. deep chains: `tblSongComponents → tblLyricLines → tblLyricLineTranslations/Annotations`). Plan: enumerate child tables via `INFORMATION_SCHEMA.KEY_COLUMN_USAGE` (handles the variant FK columns: `SongId`, `SourceSongId`, `TranslatedSongId`, `SongIdA/B`, `ResolvedSongId`) and delete inside a txn with FK checks managed; verify `affected_rows`; activity-log `song.delete`.

## Regressions the rewrite MUST fix (strategy §6a)
- **`deleteSong()` is client-only — there is NO server `delete_song` endpoint** (confirmed against the api.php action list at line ~4346). It removes the song from the in-memory list + toasts "Song deleted", but never touches the DB → the song returns on refresh. A #1010 regression (old corpus-save used to persist the removal).
- **Never report UI success without server confirmation** — several toasts fired on client intent, not the server result.
