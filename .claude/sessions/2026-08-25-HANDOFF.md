### The four failures, and why none of them announced itself

1. **#1947 — picker boot.** `bootIetfLanguagePicker()` resolved its `<datalist>`s with a
   whole-document `getElementById()` and cached the result once; two callers booted it while
   the wrapper was still detached, so every lookup was permanently `null`. Free typing still
   worked, so it read as "the picker works, it just never suggests anything". **#1849 had
   already fixed this exact class at ONE site** and its comment predicts this misread verbatim
   — but the fix was applied to a named site instead of derived from the tree. Fixed at the
   module so no caller has to remember a boot-order contract.

2. **#1949 — routing.** `.htaccess` 404s any request whose raw request line contains `.php?`.
   `/og-image` has an extensionless alias; `qr.php`, `org-logo.php` and `webhook-drain.php`
   never got one. Consequence: **no QR code and no org logo has ever rendered**, and the
   `curl ".../webhook-drain.php?key=…"` command shown on the Configuration page has always
   404'd — which is why its status line reads "Last drain: never — cron not wired" and reads
   as an operator problem. `test-qr-cuercode.js` asserted the surfaces *use* `/qr.php`, never
   that `/qr.php` **routes**.

3. **#1950 — ProPresenter.** `buildRTF()` emitted a header-less `{\rtf1\ansi\uc1 …}` with no
   font table. The RTF header grammar marks every component optional *except* `<fonttbl>`, and
   ProPresenter 7's Cocoa reader extracts nothing from such a document. The repo already knew
   this twice over — the PP6 and EasyWorship exporters both emit a `fonttbl`. **#1918 read the
   symptom as a layout fault and explicitly declined to touch the RTF because it "would break
   the existing exact-prefix assertions in tests"** — i.e. a byte-snapshot guard actively
   defended the bug. Guard now asserts structure and round-trips text back out.

4. **#1948 — translation UX.** Not a bug; the field existed behind a differently-named button.
   Two adjacent controls ("Set language" tags the *original* line; "+ Translation" adds a
   translated one) whose names didn't say so.

## Owner decisions taken (2026-08-25)

| Decision | Answer |
|---|---|
| CAPTCHA outage policy | **A** — all ticked forms degrade open on a *server-verified* outage |
| Break-glass kill-file | **Yes** — ship `CAPTCHA_DISABLED` |
| CAPTCHA provider | **Cloudflare Turnstile** |
| Language refresh | **Monthly, direct push to alpha** |
| Language scope (earlier) | Full BCP 47 registry; free text allowed as fallback with a curator surface |
| Translation UX (earlier) | Relabel + reorder the existing form |
| Routing URL shape (earlier) | Extensionless, matching the `/og-image` precedent |

**Proceeding on defensible defaults** (plan-flagged, trivially changeable): free text keeps a
**grammar floor** (well-formed-but-unregistered tags always allowed; `engli` refused), and
language remap is gated on **`manage_languages` alone**.

### The CAPTCHA asymmetry that drove decision A

During an outage today the server **already fails open for any non-empty garbage token**
(`captcha.php:443-450`); only a *missing* token fails closed (`:390-391`). So staying strict
locks out exactly one population — honest users whose widget never loaded — while a bot sending
`captcha_token:"x"` is unaffected. The grace window therefore costs almost nothing in security
and prevents a total lockout. Its allow-decisions derive **exclusively from server-side probes**;
a client hint may trigger a probe but must never influence the outcome, or it is a universal
bypass.

- **Turnstile provisioning**: create the site, register **all four** hostnames on the site key

  CAPTCHA challenge can render there. Gating `login`/`email_login` breaks sign-in on those
  targets outright, with no client-side fix.
