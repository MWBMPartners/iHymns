## The public-repository finding (needs an owner decision)

`MWBMPartners/iHymns` is a **public** repository. It has no forks and no stars, so the practical
exposure is small, but three things are readable by anyone:

1. **Seventeen ProPresenter sample files** under `_temp/` — these are copyrighted worship songs. They
   were untracked in `cea84808`, but that commit is on an unmerged branch, so twelve of them are
   still present in `origin/alpha` right now.
2. **The full lyrics of roughly 472 copyrighted songs**, inside
   `appWeb/.sql/.fulldata/ihymns-full.sql` (6.6 MB), present in `origin/alpha`'s current files.
3. **The global-admin password hash**, in the old SQLite database at `data_share/SQLite/ihymns.db`.
   It was added on 13 April 2026 and deleted on 5 June 2026, so it is gone from the current files but
   **still in the repository's history**. The owner has already changed that password as a
   precaution.

Untracking a file stops it going out in future, but does nothing about history. The three realistic
options, with their real costs:

| Option | Cost |
| --- | --- |
| **Make the repository private** | Free, immediate, and closes all three at once including history. Loses the public shop-window, which currently has nobody looking at it. |
| **Stay public and rewrite history** | Removes the files from every past commit, but **changes every commit ID in the project**. This repository quotes commit IDs in hundreds of places — 322 open issues, every handoff, and several rules in `CLAUDE.md`. All of those references would break. GitHub also keeps cached copies until you ask their support team to clear them. |
| **Stay public and only fix going forward** | What has been done so far. The lyrics stay findable by anyone who looks at history. |

**Recommendation: make the repository private.** It is free, instant and complete, and it removes the
need for the expensive history rewrite. If the project should be public later as a portfolio piece,
that is the right moment to plan a rewrite properly instead of doing one under pressure.

Tracked as **#2096**.

## Session transcripts — why the current arrangement cannot work

`.claude/sessions/` holds twelve raw conversation logs (`.jsonl`) totalling **162 MB**, alongside ten
hand-written handoff notes (`.md`) totalling **224 KB**.

The intention was that any developer, on any machine, could pick up a previous conversation. That
cannot happen, for a mechanical reason:

- Claude Code looks for a conversation in a folder named after **the full path of the project on that
  particular machine** — here, `-Users-lance-manasse-Projects-...-iHymns`. On a different computer, a
  different username, or a different folder, that name is different, so it looks somewhere else and
  finds nothing.
- `tools/sync-claude-session.sh` only copies **one way**, from the live folder into the repository.
  There is no script that puts a file back.
- Nothing in the project reads these files. Every `.claude/` document that mentions session history
  points at the hand-written `*-HANDOFF.md` notes, never at a `.jsonl`.

So the 162 MB is carried in every clone and never read, while the 224 KB of handoff notes is what
actually delivers continuity — those are plain text that a person, an editor, or any assistant can
open anywhere.

**Recommendation:** stop committing the raw logs (add `.claude/sessions/*.jsonl` to `.gitignore` and
untrack them, keeping the local copies exactly as was done for `_temp/`), and keep writing the
handoff notes. Nothing is lost, because nothing was reading them.

One reassurance from a check run this session: the scrubber in `sync-claude-session.sh` is doing its
job on the token shapes it knows about — searching the committed logs for Anthropic keys, GitHub
tokens, AWS keys and private-key headers returned only already-redacted placeholders.

## Two things that were wrong and got corrected

Worth carrying forward, because both are about *how the work was checked*, not about the code.

**1. The test runner was throwing away the failure lines.** `tools/run-php-tests.php` line 96 kept
only **one** of the two output streams:

```php
$failed[$name] = trim($stderr) !== '' ? trim($stderr) : trim($stdout);
```

About 198 of the 279 test files write their summary to one stream and their individual `FAIL:` lines
to the other, so every `FAIL` line was silently discarded whenever the other stream had anything in
it. **Fixed in `d2d29eef`.** Both runners now end with a single unmistakable line:

```
TEST RESULT: PASS (109 suites)
TEST RESULT: FAIL (4 of 279 suites failed)
```

**2. "Known baseline failure" was hiding both noise and a real bug.** This project carried six PHP
tests written off as known failures. Establishing the truth changed the picture completely:

| | Cause | Real? |
| --- | --- | --- |
| 2 suites | the container's stock 128 MB memory limit | no |
| 3 suites | PHP's `intl` extension missing, so the app took a documented weaker text-comparison path | no |
| **1 suite** | **a genuinely stale entry in the orphan allowlist** | **yes** |

**The true baseline is 278 of 279 passing, and 109 of 109 on the JavaScript side.**

The memory fix had to go in a `php.ini` inside the image, **not** as a `-d` flag on the shim: the
runner spawns each suite through `proc_open`, and a command-line flag does not reach a child process.
A flag would have fixed the direct run and left all 279 suites starved — which looks exactly like
success.

The one real failure is `test-orphan-inventory.php`, reporting that the `access_tiers` API action is
still listed as something nothing calls when somebody has since wired it. Being investigated before
anything is deleted, because a similarly named *entitlement* (`manage_access_tiers`) pollutes a
careless search.

**A question that came out of this and matters more than the tests (#2106):** the app has two
different ways of comparing text, depending on whether that `intl` extension is installed, and
**nothing anywhere reports which one is running.** That comparison decides whether a search finds a
song, whether two songs are seen as duplicates, and whether two spellings of a musician's name are
one person. CI has the extension; the local container did not; **production is unknown**.

**3. Swagger UI was reported as missing when it is not.** A search for files named "swagger" found
nothing, and that was reported as a gap. It is wrong: the browsable API documentation page has existed
for some time at `/manage/api-docs` (`appWeb/public_html/manage/api-docs.php`), pinned to Swagger UI
5.32.11 with integrity hashes, served from a CDN with a local fallback that `tools/download-vendor.sh`
fetches during deployment. It works on shared hosting because it is only PHP and static files. The
lesson is the ordinary one: search for what a thing *does*, not what you assume it is *called*.
