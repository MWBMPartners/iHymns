# 2026-09-04 — Shuffle ignored the language filter (#2069) + a process-rule fix

Branch: a new working branch `fix/shuffle-language-filter-2069` → **PR #2070 → merged to `alpha`
as `40e61de3`**, branch deleted. See "Branch model" below — §2 of the standing directives changed
this session.

## What the owner reported

> "When using the Shuffle function, and not selecting a specific songbook, Shuffle appears to
> shuffle from ALL songs, not just those in the language we selected. For example, specifically
> selecting English and Afrikaans still selects songs in other languages."

Confirmed exactly as described, and it was worse than the report: choosing a specific songbook did
not help either.

## The bug

Shuffle was the **only** public read that never asked for the reader's language choice.

The choice had been arriving at the server the whole time — `js/utils/api-client.js` attaches
`X-Preferred-Languages` to every same-origin call (rule #31) and `shuffle.js` uses that shared
client like everything else. On the server, `search`, `songs`, `songs_list`, `songbooks` and
`song_of_the_day` all read it through the shared `resolvePreferredLanguagesForRequest()`.
`case 'random'` in `api.php` simply never called it, and `SongData::getRandomSong()` had no
parameter to receive it — so the pool was every visible song.

The songbook *list* in the Shuffle window IS language-filtered, on each book's own `Language` —
which is why picking a book felt like it should work. But a book can hold songs in several
languages, and the pick inside a book was unfiltered too.

**Nothing failed anywhere.** No error, no console warning, no red test. The feature looked
entirely healthy and was wrong only in a way a person had to notice and report — the rule #30
silent-no-op class, and a textbook case of rule #35: five endpoints kept a convention, the sixth
quietly did not, and nothing checked.

## The fix (`9c742781`)

- `getRandomSong()` takes `array $langSubtags` and pushes it into the SQL via the shared
  `applyLanguageFilterSql()`, in **both** branches. It has to be in the SQL — the pick happens in
  the database (`ORDER BY RAND() LIMIT 1`), so filtering the fetched row would mean re-rolling
  until a match appeared.
- `case 'random'` resolves the list with the same shared resolver its siblings use.
- Untagged songs still always pass (that rule lives once, in `applyLanguageFilterSql()`).
- `shuffle.js` shows the server's own sentence (`data.error`) and deliberately sends no `?lang=`
  of its own — that would be a second copy of a decision the shared client already makes.

**Sub-question answered by default, flagged as trivially changeable:** an empty filtered pool
returns 404 naming the cause ("No songs available in your chosen languages") rather than silently
re-rolling unfiltered. `SongOfTheDay::pickForDate()` deliberately *does* fall back — it must yield
a pick every day or the home page looks broken. Shuffle is a button pressed on purpose, and
answering it with a filtered-out song is the complaint itself. Two lines to reverse.

## The guard (`fab525fe`)

`tests/php/test-song-language-filter-coverage.php` — tree-derived, mutation-proven, two halves:

- **A.** Every `api.php` unit calling `$songData->` must resolve the reader's languages **or**
  carry an `@lang-unfiltered: <reason>` marker. Red on the unfixed tree.
- **B.** Any `SongData` method accepting `array $langSubtags` must apply it or forward it to
  another method in the derived set. Without B, A is escapable by passing the list to a method
  that drops it.

Same `@deleted-visible:` shape as `test-song-visibility-guard.php`: whether a read *should* filter
is a judgement no scanner can make, so the decision is declared in source and the list derived
from the tree. Ten reads marked deliberate, each read before being marked — none was a second
instance of this bug.

**Eight mutations red, baseline green.** Three exist because the first draft was wrong-but-green,
which is worth carrying forward:

1. Half B first matched the signature against the unit walker's *code* view. `phpSourceUnits()`
   attributes a method's **body** to its unit but its **signature** to `(file scope)` — so it
   found exactly one "method", flagged it as a violation, and missed all five real ones. Now
   derived from signature text; the floor is what makes that collapse loud.
2. The forwarding check first asked "does the body mention `$langSubtags` anywhere, and call a set
   member anywhere" — which `if (empty($langSubtags))` beside an unrelated call satisfies while
   passing `[]` to every callee. Now scans each call's balanced argument list.
3. A bare `@lang-unfiltered:` with no reason passed, because the raw comment token carries its own
   closing delimiter and the reason check read that **as** the reason.

# Second piece of work: lyric voice parts / echoes / rounds (research only — no code)

Owner question: *"How can we better structure songs with lyrics where parts are sung by different
'groups'? Or songs with echoes, or where songs are sung in rounds?"* plus *"we should consider how
these can be entered, and stored in the backend database as well."* Worked example on screen:
**MP-0120 "Emmanuel"**, whose Verse 1 stores `WOMEN` / `MEN` / `ALL` as ordinary lyric lines.

Run as two parallel Workflows (9 + 6 agents, ~3.1M subagent tokens). **No code was changed** —
this turn produced research and three issues.

## THE HEADLINE — the feature is ~80% built and dormant

**#1137 (CLOSED) already shipped the schema**: `tblVocalParts` + `tblLyricLineVocalParts` +
`tblLyricWordVocalParts` (`appWeb/.sql/migrate-vocal-parts.php`, mirrored in `schema.sql`,
registered in `migration-registry.php` as `'vocal-parts'`). `PartKind` VARCHAR(30) already lists
`lead|main|backing|soloist|male|female|duet|group|unison|choir|congregation|cantor|descant|narrator|spoken|named-singer`.
Line↔part is **many-to-many** (so a unison/duet line carries two parts) with an `IsBackground`
flag that is literally TTML `ttm:role=x-bg` — i.e. the ECHO case. It is TTML's model transposed
one-for-one.

**The gap is not the tables.** Nothing reads `tblLyricLineVocalParts` (`?include=vocalParts`
returns the part REGISTRY only, `SongData.php:3094-3103`); there is no write path, no `PartKind`
validation map, no entry UI and no render.
`tests/php/fixtures/orphan-allowlist.php:755` states it: *"read side shipped, write side is
future feature work."*

## Framing: TWO features, not three

- **(A) Voice-part attribution + echo** — echo is a *second, background* part on the SAME line,
  not a separate construct. The M:N join + `IsBackground` were built for exactly this.
- **(B) Round / canon** — the same lines at a staggered offset; a performance structure, not line
  attribution. **Nothing models it** (no stagger/offset/entry field anywhere) and **no format can
  carry it** — TTML's is emergent, MusicXML's physical, PP7/Proclaim/VideoPsalm/EasyWorship/
  OpenLyrics/OpenSong/ChordPro have nothing. Would be new, iHymns-only schema.

## Constraints found (any implementation must respect these)

- **Never split a verse into per-voice components.** `ArrangementJson` is *"an int-array of indices
  into components[]"* (`schema.sql:310`) — inserting components silently renumbers every stored
  arrangement in the corpus. It also changes Type/Number, authoritative for CSS, chorus-repeat,
  arrangement resolution and every export keyword.
- **Never use `tblSongComponents.Label`** — display-only, CI-banned from exporters.
- **Markup shape is the highest-leverage decision.** ~14 surfaces inherit `song.php`'s HTML by
  clone or by scraping `.lyric-component`/`.lyric-line`. A voice chip as a SIBLING of
  `<p class="lyric-line">` is silently dropped from every Present slide and share snippet
  (`present-mode.js:46`, `share.js:169`) — the #1565 seven-week silent-failure class. As a CHILD,
  those ~14 come free; ~26 others re-render from JSON and need explicit wiring.
- **a11y:** today the marker has no programmatic relationship to the lines it governs (WCAG 1.3.1).
  House fix exists: nested `role="group"` + `aria-label`, visible chip `aria-hidden="true"`
  (`song.php:1307-1311`, rule #24). Reject `<dl>/<dt>/<dd>`.
- **Line grain subsumes OpenLyrics' block grain**, but the ONE assembler must fold consecutive
  same-part lines into a run or the render emits one wrapper per line.
- **Entry:** the classic editor is ONE textarea per section split on `\n` — no per-line control at
  all, and its parallel chord textarea still carries the #1263 drift bug. v2's enrichment panel is
  the only sane host. Default taken: assign a part to a SELECTED RUN of lines, v2 only.
