# TASK B2 — Offline download (songs / songbooks / catalogues): root-cause report

All paths relative to `/home/user/iHymns/appWeb/public_html/` unless noted. CSP/fragment-inline-script is confirmed NOT involved: `offline-ui.js` is a real module booted from `js/app.js:444`, `js/modules/router.js:578`, and its own DOMContentLoaded self-boot (`js/modules/offline-ui.js:245-251`); buttons are server-rendered (`includes/pages/home.php:330-336`, `includes/pages/songbooks.php:180-186`, `includes/pages/song.php:851-859`) and wire correctly.

## (a) Definitive ranked root causes

**RC1 — VERIFIED / CODE (service worker): the 2000-entry `RECENT_CACHE` cap silently destroys bulk downloads.**
`service-worker.js.php:129` (`RECENT_CACHE_LIMIT = 2000`). The bulk path (`CACHE_ALL_SONGS`, lines 856-938) writes unlimited entries, but the `CACHE_SONG` handler (lines 1110-1133, eviction at 1122-1127) trims the cache to 2000 oldest-first — and `router.js:680-687` posts `CACHE_SONG` on **every song page view**. Mechanism: download Mission Praise (3,517 songs live, per #1571; seed MP is 1,355) → 3,517 entries land → user opens ANY song → SW deletes the 1,518 oldest entries. "Download All Songbooks" (~14k songs, rule #27) → next song view deletes ~12,000. Harness (ran, replicating the exact slice arithmetic): `{"kept":2000,"deleted":1518}` and `{"kept":2000,"deleted":12001}`. The download "completes", shows green, then silently evaporates. This alone guarantees whole-corpus and large-book downloads can never persist.

**RC2 — VERIFIED code shape / CODE (server): `bulk_songs` is O(N²) per songbook; large books cannot render inside a shared-host request window.**
`api.php:1397-1456` claims (comment at 1421-1430) it skips `getSongById()` per song — that comment is **false**: `includes/pages/song.php:23` unconditionally re-fetches `$song = $songData->getSongById($songId)`, clobbering api.php:1433's `$song = $bulkSong`. The repo itself documents this (`manage/gating-noop-verify.php:104-108`: "song.php re-fetches $song from getSongById internally"). Worse, **`song.php:1470` calls `$songData->getSongs($songbook)` for prev/next navigation on every render**, and `getSongs()` (`includes/SongData.php:1798+`) has no memoisation — each call re-hydrates the ENTIRE songbook including all components (9+ queries + full lyric assembly). Plus per-song: `new SongData()` + `getSongTranslations` + INFORMATION_SCHEMA probes + tblSongLinks query (`song.php:316-393`). Net: a 3,517-song book = 3,517 whole-book hydrations + ~50k point queries in ONE request, with no `set_time_limit` (verified absent in api.php). Timing is INFERRED (no DB in this container), but this hosting's request-timeout class is a documented reality here (`js/modules/setup-bulk-runner.js` docblock; #862/#863/#868). Additionally the response for a big book is a single ~50-140MB JSON that the SW must `resp.json()` (SW line 883) — likely OOM-kills the SW process on mobile, which kills all further progress messages (the historic #452 "stuck on Downloading CH…" symptom class). Small books succeed, big ones fail/hang → exactly "doesn't seem to work properly".

**RC3 — VERIFIED / CODE (architecture): downloaded content is unreachable offline — every non-song fragment 503s.**
The shell's `#page-content` is empty server-side (`index.php:1276-1278`); every page including home loads via `/api?page=…`. The SW `/api` branch (`service-worker.js.php:444-515`) caches and offline-falls-back **only `page=song`**; `page=home|songbooks|songbook|search|settings` get a 503 JSON offline, and `router.js:451-453/486-489` turns that into a red "Failed to load page" alert. Offline chain after a successful songbook download: launch PWA → shell loads from precache → router fetches `/api?page=home` → 503 → error alert; tapping Songbooks/any songbook/Search → same. The offline search fallback (`search.js:304-431`) and slim-index precache (`/api?action=songs_index`, SW lines 202-204) are unreachable because the search page fragment itself can't load, and the shell has no search input (verified absent from index.php). The only offline reads that work are direct `/song/<id>` URLs (history/bookmarks). To the owner this reads as "downloads don't work" even when the bytes are all present.

**RC4 — VERIFIED / CODE (service worker): offline audio/sheet-music cache wiped on every deploy.**
`activate` (`service-worker.js.php:366-387`) keeps only `CACHE_VERSION` + `RECENT_CACHE`; the media bucket **`iHymns-media-v1`** (used at lines 590, 1001, 1054) is deleted on every SW activation. Cache key changes per deploy (semver × commit date, line 121), so on fast-moving alpha every deploy activation destroys all downloaded audio/PDF. Song HTML survives (RECENT_CACHE is kept) — audio does not.

**RC5 — VERIFIED / CODE (settings.js): progress UI hangs forever on any songbook-level failure; failures are invisible.**
SW counts `failed++` ONCE per failed songbook (lines 874-881, 904-913) while `total` counts songs; `settings.js:1158-1164` derives `active` from `(completed+failed) < total` and `updateDownloadProgress` (`settings.js:1196-1244`) enters its completion branch only on `completed + failed >= total` — the SW's final `done:true` (line 933-937) is never consulted, and the `warning` field is ignored. Harness (ran): one failed book out of five → bar stuck at 39%, `active:true`, completion branch never entered → "Download All" button disabled forever, no error shown. (`offline-ui.js:218-231` DOES honour `done` — only home/songbooks tiles recover.)

**RC6 — VERIFIED / MISSING-UI: catalogues (Collections) have no download — or any public — surface.**
`tblCatalogues`/`tblCatalogueSongs` are referenced only under `manage/` (admin CRUD `manage/catalogues.php`); there is no `includes/pages/catalogue*.php`, no public route, no download affordance, and no per-catalogue bulk endpoint (`bulk_songs` is keyed on `tblSongs.SongbookAbbr` only, `api.php:1403-1414`). "Downloading an entire catalogue" cannot even be attempted. (Unofficial pseudo-songbooks are distinct — they DO get tiles + working buttons via the songbook path.)

**RC7 — VERIFIED / CODE (service worker): media path-shape mismatch breaks per-book size + evict.**
`EVICT_SONGBOOK` (lines 1053-1064) and `GET_CACHE_SIZES` (lines 1094-1103) match `/data/audio/<book>/…` subdirectories, but real media URLs are flat: `bulk_audio` emits `/data/audio/<SONGID>.mp3` (`api.php:1488`) and the player uses `/data/audio/<SONGID>.mid` (`js/modules/audio.js:20-21`). Result: cached audio is never counted in Settings' per-book sizes and "Remove from offline" never deletes it (orphaned until RC4's deploy wipe).

**RC8 — VERIFIED absence / STORAGE-LIMIT: no persistence request, no quota pre-flight.**
`navigator.storage.persist()` appears nowhere in the repo; `getStorageEstimate()` (`offline-ui.js:54-74`, built for #354) is exported but **never called by anyone** (verified via grep). Size estimate (INFERRED): song fragment ≈ 12-30KB → MP ≈ 45-105MB, full corpus ≈ 170-420MB — inside Chrome quotas, plausible on iOS, but all storage is best-effort-evictable (Safari's 7-day script-storage eviction applies to non-installed usage). Audio at corpus scale (thousands of MP3s) is quota-implausible; per-URL failures are only shown as a status line count.

## (b) User-visible symptom chain per scope

- **Single song**: works for that exact URL — until RC1 eviction removes it once total entries exceed 2000. Also: the song-page button is double-wired (offline-ui `data-song-download` listener AND `router.js:671-678` → `settings.saveSongOffline`, per the deliberate "either wire path" comment at `song.php:846-850`) → two `CACHE_SONG` posts and two competing verify timers (500ms `offline-ui.js:204-207` vs 1500ms `settings.js:1434-1451`); on a slow network the 500ms check flips the button to "Download failed — tap to retry" even though the save lands moments later. Also, #1343-B soft-canonicalisation rewrites the URL bar to the PublicId while the cache key is the SongId → an offline visit to the canonicalised bookmark misses cache (severity depends on whether PublicId backfill has run — owner check).
- **Whole songbook**: small book → download succeeds, button turns green — but offline the songbook's index page 503s (RC3), so the user can't browse to the saved songs, and viewing songs online later evicts other saved books (RC1). Large book (live MP) → server timeout or SW OOM (RC2) → tile button flips to error (offline-ui `done` with `failed>0`) or, from Settings, hangs forever (RC5). Extra edge: after a hard reload the page is uncontrolled and `notifyClients` uses `matchAll({type:'window'})` without `includeUncontrolled` (line 264-267) → no progress ever arrives → spinner forever.
- **Whole catalogue**: nothing to click (RC6). If the owner means "Download All Songbooks" in Settings: RC1 guarantees eventual silent loss of ~86% of it, RC5 usually hangs the progress UI, and the audio option compounds via RC4/RC7/RC8. Note also the home/songbooks tile download ignores the "include audio" preference entirely (`offline-ui.js:234-241` admits the pref is unconsumed; only Settings' buttons dispatch `bulk_audio`, `settings.js:1085-1087/1139-1141`).

## (c) Other defects (severity)

1. MEDIUM — `bootOfflineUi()` registers a new `navigator.serviceWorker` message listener + `window` listener on every SPA navigation (`offline-ui.js:216-241` sit outside the per-node `dataset.wired` guard) → unbounded listener accumulation.
2. MEDIUM — rate limiting (`enforceReadRateLimitKeyed('bulk', 60)`, `api.php:877/1402/1471`; `includes/read_rate_limit.php:146-230`): a 429'd songbook is skipped with `failed++` and, in Settings, silently swallowed (RC5). With today's ~5 official books it likely never trips, but a many-book "Download All" (+ per-book `bulk_audio` sharing the same bucket) can. Fail-open design is correct; the client's handling of a 429 is not.
3. LOW — home/songbooks tile buttons never show pre-existing cached state on load (only `data-song-download` gets the `urlIsCached` check, `offline-ui.js:187-193`; songbook buttons always start "idle").
4. LOW — the stale `api.php:1421-1430` performance comment actively misleads maintainers (says O(N); reality is O(N²)).
5. LOW — signed-audio interplay (#1358): if gating+signing are ever enabled, the manifest caches `?exp=&sig=` URLs whose keys never match the player's fresh mints (acknowledged in SW comment 578-584). Dormant today; `CanOfflineSave`/`contentGatingApply` are verified dormant behind `content_gating_enabled='0'` and are NOT a current cause.

## (d) Fix scope per file (no code)

- `service-worker.js.php` — (RC1) exempt bulk-downloaded books from the 2000 cap (track deliberate downloads, e.g. a persisted downloaded-book set, and evict only non-downloaded "recently viewed" overflow) OR enforce a per-scope policy; (RC3) cache + offline-fall-back the `page=home|songbooks|songbook` fragments (and `page=search`), at minimum in the versioned bucket; (RC4) add `iHymns-media-v1` to the activate keep-list; (RC5) include per-song failed counts per book (or the client must honour `done`); (RC7) match flat `/data/(audio|music)/<SONGID>.<ext>` by songbook prefix (same `<ABBR>-` logic the RECENT_CACHE evict already uses at 1046-1051); add `includeUncontrolled: true` to `notifyClients`.
- `api.php` (`bulk_songs`) — make the loop actually O(N): either honour a pre-set `$song`/`$songId` contract in song.php or hoist one `getSongs($abbr)` result and derive prev/next + per-song data from it; correct the stale comment; consider chunked/paged bulk responses (the setup-bulk-runner short-request pattern, #869) so a big book never sits in one PHP request or one giant `resp.json()`.
- `includes/pages/song.php` — accept an injected `$song` and an injected `$bookSongs`/prev-next pair for bulk renders (lines 23, 1470); reuse one `SongData` instance (line 319).
- `js/modules/settings.js` — completion on `data.done`; surface `warning`/failures; stop deriving `active` purely from counts.
- `js/modules/offline-ui.js` — move listener registration behind a module-level once-guard; honour the include-audio pref (or delegate tiles to the settings flow); initial cached-state for songbook buttons; call the existing `getStorageEstimate()` pre-flight and request `navigator.storage.persist()` before bulk work.
- New (MISSING-UI): public catalogue/Collection page + a `bulk_songs`-equivalent scoped to `tblCatalogueSongs` if catalogue download is wanted.
