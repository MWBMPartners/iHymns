## [unreleased] — alpha

- feat(devices): **you can finally see — and sign out — the devices signed in to your account** (#1671 F1, remediation Batch 8) — `action=devices_list` and `action=device_signout` shipped complete and hardened in #1409/#1511 (a CSRF gate, a per-**user** rather than per-IP rate limit, and a DELETE whose `UserId = ?` sits inside the WHERE so it can only ever reach the caller's own tokens) and then had **zero callers** on web, Apple and Android alike. Somebody who signed in on a borrowed laptop had no way to revoke it. Settings → Profile now carries a "Signed-in devices" card listing each session with its platform, app version and when it was last seen, a "This device" badge on the one you are reading, and a Sign out button on every other. The current device deliberately gets **no** button — revoking it works, but it is indistinguishable from the Sign Out three inches up the page. Signing a device out is destructive, so it confirms first, announces the outcome through the shared assistive-technology announcer, and moves focus to a control that still exists rather than dropping it to `<body>` and losing a keyboard user's place. Failure kinds are told apart by **HTTP status**, never by matching the server's sentence (rule #35).

- feat(requests): **you can now find out what happened to a song you requested** (#1671 F2, remediation Batch 8) — `action=my_song_requests` has worked since #280 with **no caller anywhere**, while `song_request_submit` has always linked a submission to the signed-in user and curators on `/manage/requests` have been moving `Status` through pending → reviewed → added / declined and filling in `ResolvedSongId`. All of that was written and never read: you could send a request into silence and never learn the outcome. The `/request` page now carries a "Your requests" list below the form — each request with its status, a plain sentence saying what that status means, and a link straight to the song once one is added. It refreshes the moment a submission succeeds, so a request you just sent appears immediately rather than looking lost. Signed-out visitors get the sign-in prompt instead of a hidden section, because hiding it teaches nobody that signing in is how you track one. `Status` is a growable VARCHAR by design (rule #20), so an unrecognised value renders as itself rather than vanishing.

- feat(editor,song): **musical key, tempo and time signature are real** (#1671 F3 / #298, remediation Batch 8) — #298 shipped the `tblSongKeys` table, both endpoints, and a hidden markup block on the song page, then shipped nothing that read or wrote any of it. - fix(api): **`song_key_save` had three guaranteed 500s and nobody had ever run it** (#1671 F3, remediation Batch 8) — building the UI for a never-called endpoint found each of them within minutes, all the same species: the handler's caps did not match the column definitions, and mysqli runs under `MYSQLI_REPORT_STRICT` so a rejected write **throws** rather than returning false. It bound **NULL into `TimeSignature`, which is `NOT NULL`** — so saving a key without a time signature, the most ordinary thing a curator can do, was error 1048 and an uncaught 500; it capped `original_key` at 10 characters for a `VARCHAR(5)` column (error 1406); and it `(int)`-cast `tempo` into an `INT UNSIGNED` column, turning `"fast"` into a stored 0 and a negative number into error 1264. An unknown `song_id` hit the foreign key and threw 1452 where a 404 belongs. All four now answer with a status and a stable machine-readable `reason`. The decisions live in the pure `includes/song_key.php`, which `tests/php/test-song-key.php` **calls** — 83 assertions, every one mutation-proven to be able to fail. The gate also stopped hardcoding `['editor','admin','global_admin']` and now asks `userHasEntitlement('edit_songs', …)`: the list was byte-identical, so no role gains or loses access today, but since #1590 an operator can retune that entitlement at `/manage/entitlements` and the hardcoded copy meant the control silently did nothing here. 401 and 403 are now distinct, because the editor has to be able to say "your admin session is not linked to the app API" rather than "access denied".

- docs(api): **the OpenAPI page described a `song_key` API that does not exist** (#1671 F3) — the GET parameter was documented `songId` (the handler reads `id`), the POST body `{songId, key}` (it reads `{song_id, original_key, tempo, time_signature}`), the response a bare string (it is an object of three fields), and both were called "the caller's preferred key", implying a per-user setting rather than one shared curator-owned value. A consumer following that page could not have made a single successful call. It drifted precisely because nothing exercised it — documentation is not a mechanism (rule #35). Corrected against the handlers, including the full `reason` vocabulary.

- refactor(settings): **ONE user-preference store, and it can now be shared with a second product** (#1671 F5, remediation Batch 7) — there were TWO stores doing the same job. `action=user_settings` writes a JSON blob on `tblUsers.Settings`; it is live, synced across devices, and fed by a strict whitelist in `js/modules/settings.js`. `action=user_preferences` / `user_preferences_sync` wrote a parallel table, `tblUserPreferences` — the same concept, the same payload shape, un-namespaced, and with **no caller anywhere in the tree** (verified by file-walk across appWeb, appApple and appAndroid, because `rg` cannot see `appWeb/.sql/`). Two stores for one concept is a data-integrity trap rather than a dormant feature: whichever a future client picks, the other holds stale truth forever with nothing to say so. The duplicate pair is **deleted** — cases and OpenAPI paths — and `tblUserPreferences` drops via a manual, `confirm=1`-gated migration card that **refuses to run unless the live table is empty**, so a row written by some out-of-repo caller is a hard stop rather than silent data loss. What survives gains the write contract that makes a shared store possible: **POST may name a `namespace`** (`^[a-z][a-z0-9_]{1,31}(\.[a-z][a-z0-9_]{1,31})?$` — `ihymns.web`, `ilyricsdb`, `apple`) and the server replaces **only that subtree**, leaving siblings untouched; GET accepts the same parameter to read one back. The merge is at the namespace **root and deliberately not recursive** — a deep merge makes deleting a key impossible, because the client sends the subtree without it and the merge keeps the old value, silently, forever. Caps are **413 refusals, never truncations** (the rule #1649/#1662 established the hard way), and the total-blob backstop is measured against the **result** of the write rather than its input, so an account that is already over it can still shrink itself back under instead of being trapped above the ceiling. Omitting `namespace` is byte-for-byte today's whole-blob replace, so `settings.js` and the shipped native apps are untouched — with the corollary stated in code, docs and the spec: **a namespace-less POST still clears every namespace**, so isolation holds once every writer is namespaced. The decisions live in pure functions in `includes/user_settings.php` and are pinned by `tests/php/test-user-settings-namespace.php`, which **calls them and asserts the answers** rather than pattern-matching the source — the lesson of `test-transaction-fatal.php`. Ten mutations (deep merge, sibling wipe, `$` for `\z`, case-insensitive names, cap-on-input, truncate-not-reject, `[]` for `{}`, null-for-absent, encoder flags, skipped validation) were each proven to turn it red, and three correct-but-textually-different rewrites proven to leave it green.

- feat(setlists): **no cap, explicit deletion, and an optional expiry — a set list now goes away only when you say so** (#1661) — the 50-set-list cap was never intentional and never specified; it was simply the number somebody typed, and #1649 had to work around it because the server *inferred* deletion from a set list being missing from a sync payload. Those are different facts, and conflating them is what silently ate the tail of large collections. The cap is **removed entirely** — the only limit left is a generous 4 MiB whole-body ceiling that answers **413**, a loud, retryable rejection instead of an invisible, permanent truncation. Deletion becomes something a client **says**: a new `deleted: [id, …]` list writes a permanent tombstone (`tblUserSetlistTombstones`), and **the presence of that key — even as `[]` — is what marks a protocol-2 client**, for which absence-based deletion is retired outright. A tombstoned id is dead **forever**; re-creating mints a fresh client id. That rule is deliberately deterministic rather than a timestamp comparison against the incoming `updatedAt`, because a client clock is not evidence — a device running fast would otherwise resurrect everything it had ever deleted. Separately, each set list may now carry an **optional expiry** (`tblUserSetlists.ExpiresAt`, `NULL` = never expires, which is what every existing set list gets); the **server** converts an expired set list into a tombstone with `reason: "expired"` on the next read, so expiry and deletion propagate through one mechanism and two devices with different clocks can never disagree mid-service. **Native app sync behaviour is completely unchanged** — the Apple and Android clients never send `deleted`, so they stay on the legacy, #1649-guarded path, and their decoders ignore the added response fields. ⚠️ The migration is **web-run**: apply "Setlist tombstones + optional expiry" on `/manage/setup-database` for each environment after deploy; until then every new read is existence-gated and behaviour is byte-for-byte what it is today.
